MediUM+ API Reference
Base URL: https://medium-backend-md5a.onrender.com
Every endpoint below has the base URL included in full in the index table — copy-paste any URL directly into your fetch() calls. This doc is updated after every batch of backend work.
How Every Response Looks
Success:
{
  "success": true,
  "message": "Human-readable message",
  "data": { }
}
Error:
{
  "success": false,
  "message": "Human-readable message",
  "code": "SOME_CODE"
}
"message" is always safe to show the user directly. "code" is there in case you want to handle a specific situation differently in your JS.
Authentication
After a successful login, you receive a "token". Store it (localStorage is fine). For any endpoint marked Protected, attach it as a header:
Authorization: Bearer <the token>
Missing/expired/invalid token → 401 with code "NOT_LOGGED_IN" or "INVALID_TOKEN". Logged in but wrong role for that endpoint → 403 with code "FORBIDDEN".
MediUM+ is Multi-Tenant — What This Means For You
Every hospital using MediUM+ is its own separate "tenant". Patients and doctors register UNDER a specific hospital (a dropdown, populated from endpoint 9). A patient or doctor only ever sees data belonging to their own hospital — doctors, appointments, everything is automatically scoped behind the scenes. You do not need to filter by hospital yourself; the backend already guarantees this.
Roles, in order: superadmin (one, platform-wide, approves hospitals) → admin (one per hospital, approves that hospital's doctors) → doctor (approves appointments) → patient (books appointments).

New in This Batch — Admin Module
Endpoints 34–41 are brand new. Here is the context needed to build the admin dashboard UI around them:
Patients are never permanently deleted. "Delete" in the admin UI should call deactivate (endpoint 36), not remove the record — appointment history must stay intact. A separate activate endpoint (37) exists to undo this.
Admin CANNOT edit a patient's blood group. That field is intentionally excluded from endpoint 35 for safety — only the patient themselves or a doctor should be able to set it. If your edit form includes a blood group field, sending it will simply be ignored, not an error.
Admin can CANCEL any appointment (endpoint 39) for operational reasons (e.g. doctor unavailable, hospital closure), but CANNOT approve/reject bookings — that remains solely the doctor's decision (endpoints 25/26 from the Doctor section).
Every sensitive admin action (patient edits, deactivate/activate, appointment cancellation, doctor approve/reject) is now recorded in an audit trail, viewable via endpoint 41. Good candidate for an "Activity Log" or "Recent Actions" panel in the admin dashboard.
New in This Batch — Forgot Password & Allergies
Endpoints 42–43 are brand new, plus one field addition to the Patient module. Context for the frontend:
Forgot Password is now a two-step flow: endpoint 42 sends a reset link to the user’s email if the account exists (it always returns the same generic success message either way, so it can’t be used to check which emails are registered), and endpoint 43 completes the reset using the token from that link.
UPDATE: the link now points to {CLIENT_URL}/forgot_password_account_recovery.html?token=<token> — matching the frontend’s existing page (it was originally reset_password.html, changed to avoid needing a new page). The frontend still needs to add a conditional “enter new password” step to this page when a token is present in the URL, POSTing to endpoint 43.
The reset token is single-use and expires 30 minutes after the email is sent. A stale or already-used token returns 400 INVALID_OR_EXPIRED_TOKEN — the reset page should show a friendly "this link has expired, request a new one" state for this, not a raw error.
Both endpoints share the same rate limit as login/register (20 requests per 15 minutes per IP) — if you’re testing repeatedly, you may hit AUTH_RATE_LIMITED.
Patient.allergies is a new field — an array of strings, e.g. ["Penicillin", "Peanuts"]. It’s now part of endpoint 15 (update profile), endpoint 16 (digital card), and the printable card PDF (endpoint 17, back page). Like blood group, it is intentionally NOT editable by admin (endpoint 35) — only the patient or a doctor can set it.

18. Book an Appointment
POST  
https://medium-backend-md5a.onrender.com/api/patients/appointments
Access: Protected — Patient only
Body:
{
  "doctorId": "665f...",
  "date": "2026-07-20",
  "timeSlot": "09:00 AM",
  "visitType": "general_consultation",
  "reason": "Routine checkup"
}
visitType is REQUIRED — must be one of the values from endpoint 28 (e.g. "general_consultation", "follow_up", "new_patient_exam", "minor_procedure", "other"). Its duration determines how many 30-min slots the appointment actually blocks.
reason is required ONLY when visitType is "other" — otherwise optional.
timeSlot must be one of the values returned by endpoint 30 for that SAME visitType — the backend re-validates this regardless.
Success response:
{
  "success": true,
  "message": "Appointment booked successfully and is pending doctor approval",
  "data": { "appointment": {...} }
}

New in This Batch — Doctor Detail View, Notifications & Reminders
Endpoints 44–48 are new, plus two existing endpoints picked up new fields/filters. Context:
Doctor registration (endpoint 2) and List Doctors (endpoint 29) now support gender and languages — both optional, settable only at doctor registration for now (no edit-profile endpoint exists yet). Endpoint 29 also takes ?gender= and ?language= as new filters.
Endpoint 44 (single-patient view for a doctor) only works if the doctor has actually had at least one appointment with that patient — otherwise it returns 403, not the patient’s data. This is deliberate, not a bug: a doctor shouldn’t be able to browse arbitrary hospital patients by guessing an id.
The Notification model already existed in the schema before this batch — endpoints 45–48 are the first endpoints that actually expose it. Every notification belongs to exactly one user; there’s no cross-user access possible.
Notifications now fire automatically (no new endpoint calls needed) when: an appointment is approved/rejected/cancelled/rescheduled by either side, and when a doctor account is approved/rejected. Build the bell icon against endpoints 45 (list) and 46 (unread count) and it’ll start populating immediately from existing actions.
Appointment reminders are NOT an endpoint — they’re a background job that runs automatically every 15 minutes and creates a notification (type: appointment_reminder) plus sends an email, 24hrs and 1hr before a confirmed appointment. Nothing for the frontend to call; just render the appointment_reminder notification type like any other when it shows up in endpoint 45.
